# Review of 104: release-only versioning

**Verdict:** The mission identifies the current version churn correctly and reflects the owner’s decisions. It needs a more precise version calculation and a release failure plan before implementation.

1. **High — The proposed patch calculation would jump immediately.** The mission says the patch is the number of commits since the last release tag, but the only `v*` tag is `v0.1.0`; at the reviewed HEAD, `git describe` reports 1,168 commits since it, while `package.json` is `0.1.741`. The first new Pages build would therefore be `0.1.1168`, not the next patch after `0.1.741`. A push containing several commits can also skip patch numbers. Evidence: [mission §version scheme](/Users/sal/PycharmProjects/simulation_of_boring_things/doc/prompts/104-release-only-versioning.md:13), [package.json](/Users/sal/PycharmProjects/simulation_of_boring_things/package.json:3). **Recommendation:** Define a transition baseline and say whether “next patch” means per commit or per push. Test the first build before and after `v0.2.0`.

2. **High — CI must fetch and validate release history.** The current main workflow fetches full history, but the proposed checkout change does not say to retain `fetch-depth: 0` and tags. The release workflow currently uses a shallow checkout. A missing tag could silently produce a wrong derived version, and its current checks establish only that the tag matches `package.json` and a changelog heading—not that it is annotated, on `main`, or points to the release commit. Evidence: [ci.yml](/Users/sal/PycharmProjects/simulation_of_boring_things/.github/workflows/ci.yml:27), [release.yml](/Users/sal/PycharmProjects/simulation_of_boring_things/.github/workflows/release.yml:18). **Recommendation:** Fetch tags and sufficient history in both workflows; fail closed if the expected release tag cannot be verified. Check tag type, target commit, lockfile versions, and release commit identity before publishing.

3. **High — “Failure at any step leaves the tree and tags as they were” is too strong.** The proposed script writes three files, commits, tags, then pushes; failures in those later steps cannot satisfy that promise without explicit recovery. Another session can advance `origin/main` after the initial check. Separate commit and tag pushes can also leave a partial remote release. Evidence: [mission §2 and acceptance criteria](/Users/sal/PycharmProjects/simulation_of_boring_things/doc/prompts/104-release-only-versioning.md:24). **Recommendation:** Recheck the remote immediately before publication, use an atomic branch-and-tag push, and specify safe local rollback and retry behavior for failures after writing or committing. Test those failure points, including a concurrent push.

4. **Medium — The CI guard needs a defined range and stronger invariant.** “Fails when `package.json`’s version changes in a commit that is not a `Release v…` commit” leaves batch pushes, pull requests, and the migration commit unspecified. A commit message alone does not prove that the version matches its tag or that both lockfile root fields match. Evidence: [mission §4](/Users/sal/PycharmProjects/simulation_of_boring_things/doc/prompts/104-release-only-versioning.md:26), [build.ts](/Users/sal/PycharmProjects/simulation_of_boring_things/scripts/build.ts:44), [package-lock.json](/Users/sal/PycharmProjects/simulation_of_boring_things/package-lock.json:1). **Recommendation:** Check every commit in the pushed range, with an explicit migration exception, and validate all three version fields against the release tag.

5. **Medium — The deployed-version paths need one source of truth.** Today `build.ts` supplies `VITE_VERSION`; `vite.config.ts` otherwise reads `package.json`; `VERSION` feeds the title screen, manual, and settings panel. The mission says both that a plain build uses the package version and that it displays a derived patch. Those instructions conflict unless the derived value is passed into the bundle consistently. Evidence: [build.ts](/Users/sal/PycharmProjects/simulation_of_boring_things/scripts/build.ts:31), [vite.config.ts](/Users/sal/PycharmProjects/simulation_of_boring_things/vite.config.ts:38), [version.ts](/Users/sal/PycharmProjects/simulation_of_boring_things/src/game/version.ts:23), [manual.ts](/Users/sal/PycharmProjects/simulation_of_boring_things/src/manual/logic/manual.ts:26). **Recommendation:** Compute and validate the effective version once in the build path, pass it through `VITE_VERSION`, and test the title screen, manual, and settings against that value. Define local, dirty, missing-tag, and tagged-release behavior.

6. **Medium — The itch.io move needs a complete deploy contract.** Today `ci.yml` uploads `dist` as an artifact and its itch job calls butler with `BUTLER_API_KEY`; `release.yml` has no itch job. Moving the upload requires an artifact or same-job `dist` path, the secret, channel, `--userversion`, and an explicit failure when the secret is absent. Evidence: [ci.yml](/Users/sal/PycharmProjects/simulation_of_boring_things/.github/workflows/ci.yml:63), [release.yml](/Users/sal/PycharmProjects/simulation_of_boring_things/.github/workflows/release.yml:40). **Recommendation:** Spell out the release-only upload steps and verify the shipped bundle and butler version are exactly `X.Y.Z`. Keep Pages’ `dist` upload on main pushes.

7. **Low — The research note still describes rejected choices.** It proposes patch-default releases, `+N` labels, and itch uploads on every main push; the mission records later owner decisions that supersede all three. The live README and devlog instructions still describe build-number commits and main-to-itch deployment, as the mission recognizes. Evidence: [research §proposal](/Users/sal/PycharmProjects/simulation_of_boring_things/doc/research/104-release-only-versioning.md), [README](/Users/sal/PycharmProjects/simulation_of_boring_things/README.md:72), [devlogs README](/Users/sal/PycharmProjects/simulation_of_boring_things/doc/devlogs/README.md:15). **Recommendation:** Mark the research proposal as superseded where it differs, so implementation follows the mission alone.

**Recommended mission edits:** Define the transition baseline and patch-count rule; require full tag history and fail-closed tag checks; specify one effective bundled version; add lockfile and pushed-range guard criteria; describe atomic push, concurrency, rollback, and retry behavior; enumerate the release workflow’s butler path, secret, and `--userversion`; and add acceptance tests for missing tags, the first migration build, concurrent pushes, and failures after the bundle succeeds. A simpler implementation would keep the version calculation in `build.ts` and let `vite.config.ts` consume its `VITE_VERSION`, avoiding two independent calculations.
