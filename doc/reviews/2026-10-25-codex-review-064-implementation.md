# Review of prompt 064 implementation since `13c20df`

## What is right

- The work follows the revised build order through step 6: it adds typed model references, a pinned unbound set, prescribed plumber fittings, a jacuzzi schematic, model keyed valves, and a testable hall contents builder. The jacuzzi schematic test checks unique IDs, zero plumber additions and unvalved gravity overflows (`jacuzzi-schematic.test.ts`).
- `model-valves.ts` derives PL3 valve tags, names and route descriptions from schematic fittings and link endpoints. `installed-valves.ts` removes the old PL3 register entries and uses fitting IDs as valve state keys. `save.ts` migration 26 resets old state as the owner allowed.
- The focused tests pass: 3 files, 25 tests (`jacuzzi-schematic`, `world-in-model`, `world-in-model-scene`). The scene test checks actual meshes made by the extracted plant and hall builders, a useful complement to the data inventory.

## Bugs, gaps and rule violations

1. **The make-up valve does not have one state.** In `world.ts`, `applyAction` handles `plant/valve` by changing only `installedValves` (lines 345–358), while `jacuzziPlumbing` still requires `pools.pool_03.makeUp` (lines 759–770). `pool/make-up` writes both (lines 394–405). After the pool action shuts make-up, opening the physical/model valve via `plant/valve` leaves the tank unable to refill. The valve action and the simulated flow therefore disagree. The drain has the same duplication: `jacuzziDrainDown` writes a fitting state and `pools.pool_03.drainDown`, while `jacuzziDischarging` reads only the latter (lines 295–303, 875–877). This is synchronized through current actions, but still violates the single source of truth.
2. **The zero scene result excludes live things and masks pool fittings.** `world-in-model-scene.test.ts` builds only `createRoomEquipment` plus `cabinetServices` for the plant room (lines 54–73); `plant-room-shell-room.ts` adds other scene contents. `pool-hall-room.ts` adds the working plant door after `buildPoolHallContents` returns (lines 238–252), so the hall test does not see it. `buildPoolHallContents` marks every initial child of `createPoolHall` decorative (lines 887–895), yet `pool-hall.ts` puts the jacuzzi's wall jets, main drains and underwater light into that group (lines 855–881). Those engineering fittings pass the test as scenery without model identities.
3. **The inventory and scene checker prove only ID membership.** `world-in-model.ts` `isBound` (lines 102–110) and `world-in-model-scene.ts` `unboundInScene` (lines 14–29) accept any existing node, fitting or link of the stated sort; they do not check that a drawn valve is on its actual run, or that a pipe matches its model route. `identities` numbers repeated kind/name strings (lines 279–286), so its “unique identity” test is tautological. `MODELLED_WORLD_ROOMS` is plant rooms only (line 298); the pool hall is absent from the pinned identity inventory.
4. **The plumber does not yet own the drawn pipework.** `cabinet-pipes.ts` `cabinetPipes` still calculates the old runs and valve coordinates, then `bindToModel` assigns matching link IDs and swaps valve names (lines 1026–1055). The scene is consequently routed by authored geometry, not the enhanced network's router, and has no route score. `roomModel` in `world-in-model.ts` validates pipes against base `JACUZZI_LINKS` (lines 85–99), although `expandForPlumbing` splits links at fittings into different enhanced edges. This is the acknowledged unfinished step 7, and the central remaining acceptance gap.
5. **Prescribed fitting metadata is incomplete.** `plumbing-expansion.ts` `GivenFitting` (lines 79–89) has no actuation/operator field, despite the adopted prompt requiring it. `cabinet-pipes.ts` keeps `run.valve.operator` and position from the old visual run; `bindToModel` changes only its displayed ID and name. The schematic cannot determine how each fitting is worked or where it is drawn.
