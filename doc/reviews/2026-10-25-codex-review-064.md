## Risks and gaps

- **A model ID is not yet a runtime valve key.** [world.ts](/Users/salimfadhley/workspace/simulation_of_boring_things/src/game/world.ts) stores `installedValves` by asset ID; `plant/valve` resolves commands through `installedValveByCommandId`. [jacuzziPaths](/Users/salimfadhley/workspace/simulation_of_boring_things/src/game/plant/jacuzzi.ts) reads hard-coded `valve-…` IDs. The tub drain is different again: [cabinetServices](/Users/salimfadhley/workspace/simulation_of_boring_things/src/toolkit/gallery/views/cabinet-services.ts) dispatches `pool/drain-down` and reads `pools.pool_03.drainDown`. The make-up command writes both the installed valve and a pool flag. Changing visual bindings alone will leave these paths split.

- **`expandForPlumbing` cannot yet consume specified valves.** [PlumbNode, Fitting and `expandForPlumbing`](/Users/salimfadhley/workspace/simulation_of_boring_things/src/game/plant/plumbing-expansion.ts) have no input for a valve’s link position, function, individual normal state or prescribed operator. Expansion generates fittings from kind-based rules and one global `normally` value. It must match a schematic valve to a required fitting without generating a duplicate, retain its identity and order in `along`, and report each genuinely missing fitting. Shared ports need particular care.

- **The Olympic room is an example with known exceptions, not a complete template.** [plumbOlympic](/Users/salimfadhley/workspace/simulation_of_boring_things/src/toolkit/gallery/logic/olympic-plumbing.ts) still adds a regulating valve and tap-offs outside the expansion, and places some shared fittings specially. [Prompt 063](/Users/salimfadhley/workspace/simulation_of_boring_things/doc/prompts/done/063-component-information-remediation.md) records the resulting unbound items. Prompt 064 should say which plumbing and drawing path the jacuzzi will reuse and require every exceptional fitting to enter its enhanced network.

- **The pool hall needs an actual binding inventory.** [pool-hall-room.ts](/Users/salimfadhley/workspace/simulation_of_boring_things/src/toolkit/gallery/rooms/pool-hall-room.ts) creates the tub, wall plate, speakers, fibre wall and door directly. [drawnThings](/Users/salimfadhley/workspace/simulation_of_boring_things/src/toolkit/gallery/logic/world-in-model.ts) currently lists plant-room data only. A separate, hand-maintained list could pass while a new scene object goes unnoticed. Derive the listing from the same hall specifications or builder data, including controls inside the cabinet and tub.

- **“Decorative” needs a firm boundary.** A working door, speaker, fibre illuminator, gauge, valve panel or START/STOP plate cannot be decorative under the project rule that engineering items work. Architectural shell, signs and genuinely inert finish can be. Enforce exactly one binding form—model reference _or_ decorative—and validate that a model reference has the right node, fitting or link type. Pipes should bind to links; `node` is an imprecise field name for them.

- **A zero count is insufficient proof.** [world-in-model.test.ts](/Users/salimfadhley/workspace/simulation_of_boring_things/src/toolkit/gallery/logic/world-in-model.test.ts) pins totals, so one unbound item can replace another without changing the count, and blanket decorative marks can make the jacuzzi reach zero. It does not prove that a bound control changes the state read by the simulation, or that every drawn pipe corresponds to its routed link.
