## 1. Summary

- Web games are sold on Steam in Electron or NW.js all the time; nothing in Valve's rules forbids it, and Steam only needs an executable it can launch. CrossCode shipped on NW.js ([Summer Engine guide](https://www.summerengine.com/make-great-games/threejs-game-on-steam), written after August 2026).
- **(judgement)** Electron is the right wrapper for this game: it bundles its own Chromium, so the WebGL 2 renderer, WebAudio and Gamepad API behave exactly as they do in Chrome today on every platform, including a native Linux build for the Deck. Tauri and Neutralino are much smaller but use the system web view, which on Linux is WebKitGTK, whose WebGL path Tauri's own docs warn can be silently slow ([Tauri, Linux graphics issues](https://v2.tauri.app/develop/debug/linux-graphics/), updated 2026-06-15).
- Steamworks (achievements, overlay, the cloud API) is optional. Steam Auto-Cloud can sync a save file with no SDK code at all ([Steam Cloud docs](https://partner.steamgames.com/doc/features/cloud), read 2026-10-22). **(judgement)** Ship first with no Steamworks SDK: it avoids the overlay's known trouble in Electron and a GPL-versus-proprietary-SDK question (section 8).
- The codebase is in good shape for packaging (relative `base`, dynamic imports that bundle cleanly, no workers, no `SharedArrayBuffer`, Xbox-named gamepad bindings), but a few things block a good Steam or Deck release: saves live only in `localStorage`; sound waits for a mouse or keyboard event, so a player using only the Deck's controls would never hear anything; the start screen is an HTML list of links that a controller cannot drive; there is no pause or quit on the gamepad; one texture path is absolute (`/posters/…`); and one sound is not cleared for distribution. Section 9 lists the changes.
- Cost to sell on Steam: US$100 per game, recouped after US$1,000 adjusted gross revenue; 15–30 days of onboarding, a 30-day wait between paying and releasing for a first title, a "coming soon" page live for at least two weeks, and a 1–5 day review ([Steam Direct](https://partner.steamgames.com/steamdirect), read 2026-10-22).

## 3. Can a web game be sold on Steam, and in what wrapper?

### Facts

- Steam takes any build it can launch; there is no engine requirement. Developers have long shipped HTML5 games on Steam in Electron (for example [Drawize, "How to release an HTML5 game on Steam"](https://www.drawize.com/blog/tech-how-to-release-html5-game-on-steam), and a developer's 2023 write-up of putting a browser game on Steam for Linux with Electron, [Schemescape, part 2](https://log.schemescape.com/posts/game-development/web-game-on-steam-for-linux-2.html), 2023-08-26).
- **Electron** bundles a pinned Chromium and Node. Electron 45.0.0 went stable on 2026-10-20 with Chromium M156; the team supports the latest three stable majors, so each major has roughly an eight-month life ([Electron release schedule](https://releases.electronjs.org/schedule), read 2026-10-22; [Electron timelines](https://www.electronjs.org/docs/latest/tutorial/electron-timelines)). npm shows `electron` 45.0.0 published 2026-10-21, `@electron-forge/cli` 8.0.1 (2026-09-29) and `electron-builder` 26.15.3 (2026-06-09) (npm registry, read 2026-10-22).
- **NW.js** also bundles Chromium and lets page code call Node directly; CrossCode shipped on it ([Summer Engine guide](https://www.summerengine.com/make-great-games/threejs-game-on-steam)). `nw` 0.119.1 was published to npm on 2026-10-22.
- **Tauri** (`@tauri-apps/cli` 2.12.4, 2026-10-21) uses the operating system's web view: WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux. Its docs say a minimal app can be under 600 KB ([Summer Engine guide](https://www.summerengine.com/make-great-games/threejs-game-on-steam), quoting Tauri). On Linux, Tauri's own docs warn that WebGL "can fail silently": a context can be created on a software rasteriser or slow presentation path with no error, WebKitGTK masks the GPU name (it reports "Apple GPU"), and the symptoms are low frame rates and input lag in WebGL-heavy views; most reported breakage is on NVIDIA ([Tauri, Linux graphics issues](https://v2.tauri.app/develop/debug/linux-graphics/), updated 2026-06-15).
- **Neutralinojs** (`@neutralinojs/neu` 11.8.0, 2026-10-06) also uses the system web view, so it shares Tauri's Linux position.
- Electron on Linux under Steam: several developers found their Electron game would start from a terminal but crash or hang when launched by Steam or on a Deck, fixed by the `--no-sandbox` switch (Chromium's seccomp sandbox appears to conflict with Steam's own container) ([steamworks.js issue #42](https://github.com/ceifa/steamworks.js/issues/42), 2022-09-22; [PR #49](https://github.com/ceifa/steamworks.js/pull/49), 2022-10-28; [Schemescape](https://log.schemescape.com/posts/game-development/web-game-on-steam-for-linux-2.html); [Electron issue #18265](https://github.com/electron/electron/issues/18265)). The same 2023 write-up saw a 25-pixel cursor offset in a windowed Electron build under Proton, but not in full screen, and shipped a native Linux Electron build instead.
- Electron's security guidance prefers a custom protocol over `file://`; `protocol.registerSchemesAsPrivileged` with `standard`, `secure` and `supportFetchAPI`, then `protocol.handle`, serves the build with working relative URLs, `fetch()` and web storage (web storage is disabled for non-standard schemes) ([Electron protocol API](https://www.electronjs.org/docs/latest/api/protocol), read 2026-10-22).

### Trade-offs

|                       | Electron                                                                               | NW.js                     | Tauri / Neutralino                                                                        |
| --------------------- | -------------------------------------------------------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------- |
| Engine                | Its own Chromium, chosen by you                                                        | Its own Chromium          | System web view: WebView2 (Chromium, updated by Microsoft), WKWebView (Safari), WebKitGTK |
| Download              | Large: **(judgement)** of the order of 100 MB on top of the game's 15 MB               | Similar                   | Small: a few MB on top of the game                                                        |
| WebGL on Windows      | Same as Chrome                                                                         | Same as Chrome            | WebView2 is Chromium, so same as Edge                                                     |
| WebGL on Linux / Deck | Same as Chrome on Linux                                                                | Same as Chrome on Linux   | WebKitGTK: the risk Tauri's docs describe                                                 |
| Version control       | Exact: you pick the Chromium                                                           | Exact                     | None on Windows (Evergreen WebView2) and macOS; the distribution's WebKitGTK on Linux     |
| Steamworks bindings   | steamworks.js, steamworks-ffi-node, Greenworks                                         | steamworks.js, Greenworks | Rust `steamworks` crate (repository pushed 2026-10-19)                                    |
| Save location         | `app.getPath('userData')` (`%APPDATA%\<name>` on Windows, `~/.config/<name>` on Linux) | similar                   | Tauri's app data directory                                                                |

**(judgement)** For a WebGL 2 first-person game whose most likely second platform is the Deck, the deciding row is WebGL on Linux, and Electron wins it. Its size is the price, and for a game on Steam the price is small: Steam handles downloads and updates (no auto-updater is needed in the app). Tauri would be my second choice only if the game shipped as a Windows build under Proton on the Deck, and I found no reports either way on WebView2 under Proton, so that would need testing first.

## 4. Steamworks from a web wrapper

### Facts

- **steamworks.js** (Rust, via napi): MIT, supports Electron and NW.js, achievements, cloud, Workshop ([Summer Engine guide](https://www.summerengine.com/make-great-games/threejs-game-on-steam)). Its last npm release is 0.4.0 of 2024-08-06, although the repository was last pushed on 2026-04-08 and has 66 open issues and pull requests (npm registry and GitHub API, read 2026-10-22). In Electron it must be used from the main process, or from the renderer with `nodeIntegration: true` and `contextIsolation: false`; the Steam redistributable library must be copied into the build root ([steamworks.js README](https://github.com/ceifa/steamworks.js)).
- **Overlay in Electron**: steamworks.js offers `electronEnableSteamOverlay()`, but its open issues include "Overlay not working" (#160, 2024-08), "Overlay shows as white" (#116), "Overlay Woes on Linux build" (#195, 2025-07, Shift+Tab doing nothing on a native Linux build) and "doesn't seem to work for Mac" (#50) (GitHub issues, read 2026-10-22). Greenworks' troubleshooting notes say the overlay needs frames drawn continuously, may need `--in-process-gpu`, and only appears when launched through Steam ([Greenworks troubleshooting](https://github.com/goldfire/greenworks/blob/master/docs/troubleshooting.md)); Drawize found `--ignore-gpu-blacklist` made it show but caused crashes, and accepted that some players would have no overlay ([Drawize](https://www.drawize.com/blog/tech-how-to-release-html5-game-on-steam)).
- **steamworks-ffi-node** (Koffi FFI; npm 0.11.3 of 2026-09-24) works round the overlay by copying Electron's frames into a separate native window (OpenGL on Windows and Linux, Metal on macOS) into which Steam injects its overlay; Linux needs X11 (no Wayland) and it is stated to have been tested in the Deck's Desktop Mode ([steamworks-ffi-node overlay docs](https://github.com/ArtyProf/steamworks-ffi-node/blob/main/docs/STEAM_OVERLAY_INTEGRATION.md), read 2026-10-22).
- **Greenworks**: the npm package was last published in 2016 (builds come from GitHub); the repository was last pushed on 2025-11-23. Its maintainers call it best-effort, and new projects usually start with steamworks.js ([Summer Engine guide](https://www.summerengine.com/make-great-games/threejs-game-on-steam)).
- **Steam Auto-Cloud** needs no code: you name root folders in the Steamworks settings (for example `WinAppDataRoaming` for `%USERPROFILE%\AppData\Roaming\`, `LinuxXdgDataHome`, `MacAppSupport`), with sub-paths, patterns and cross-platform overrides, and Steam syncs matching files at launch and exit. Valve recommends small files, a per-user sub-folder with `{64BitSteamID}`, and keeping machine-specific settings out of the cloud. The API alternative (`ISteamRemoteStorage`) gives finer control and supports Dynamic Cloud Sync for the Deck's suspend and resume ([Steam Cloud docs](https://partner.steamgames.com/doc/features/cloud), read 2026-10-22).

### Judgement

- Achievements are the only Steamworks feature this game would obviously want, and they are not needed on day one. Auto-Cloud covers saves without the SDK.
- If the SDK is added later, steamworks-ffi-node is the more actively released library today, and steamworks.js the more widely used; call either from Electron's main process over IPC rather than turning on `nodeIntegration` in the renderer. Treat the overlay as best-effort and do not make anything depend on it.
- Read section 8 on the GPL before linking the SDK.

## 5. Steam Deck

### Facts: the Deck Verified criteria

From [Valve, Steam Deck compatibility review](https://partner.steamgames.com/doc/steamdeck/compat) (read 2026-10-22; no date on the page):

- **Input**: the default configuration must give access to all content with the Deck's physical controls, without the player changing settings. On-screen glyphs must match the active input (Deck or Xbox names), and keyboard or mouse glyphs must not appear while the controller is in use. Steam Input is strongly recommended. Text entry must use Steamworks' on-screen keyboard or a controller-driven entry of the game's own.
- **Performance**: a playable frame rate by default, defined as 30 fps at 800p.
- **Seamlessness**: no warnings that the hardware or Linux is unsupported. Any launcher must meet the same rules, including full controller navigation, and needing to go through a launcher at all is strongly discouraged.
- **Display**: run at a resolution the Deck supports, 1280×800 (preferred) or 1280×720. Text readable at 30 cm: the smallest font at least 9 px tall at 1280×800; 12 px and user-adjustable text size are recommended.
- **Linux or Proton**: Valve tests the native Linux build first if there is one; if it fails or has significant problems, it tests the Windows build under Proton, and submits whichever is better. A re-review can name the platform.
- **Hardware**: AMD APU with an RDNA 2 GPU of 8 compute units at 1.0–1.6 GHz (up to 1.6 TFLOPS FP32), sharing 16 GB of LPDDR5 with the CPU ([PC Gamer](https://www.pcgamer.com/uk/steam-deck-performance-expectations); [Gigazine](https://gigazine.net/gsc_news/en/20230306-steam-deck-apu)).
- **Gamepad in a browser engine**: through Steam Input the Deck appears to the W3C Gamepad API as a standard-mapped Xbox-layout pad; the back grip buttons are not in the standard mapping, and Steam Input can create duplicate virtual pads that need de-duplicating (third-party: [a web app's pull request](https://github.com/got-feedBack/feedBack/pull/1001); [Brainhub](https://brainhub.eu/library/making-electron-apps-steam-deck-compatible)).
- WebGL in Chrome on a Deck: one developer found a WebGL game noticeably slower there than on an M1 Mac mini ([Babylon.js forum](https://forum.babylonjs.com/t/steam-deck-linux-and-chrome-performance/47555), anecdotal). I found no published three.js benchmarks on the Deck.

### How the game measures up (judgement, from reading the code)

- **Controls**: walking, looking, using, knobs, zoom, crouch and torch are all on the pad, with Xbox glyphs. Missing: a Start/Menu button for pause, settings, the room list and quit; and the "release" action, which has no pad binding (`src/toolkit/controls/logic/controls.ts`). Help text currently lists all bindings for the active mode, which is the right behaviour for the glyph rule.
- **Start screen**: `index.html`'s room list is mouse and touch only, so it fails the launcher rule as it stands. The desktop build needs a title screen driven by the pad, and probably a curated list without the development rooms.
- **Audio**: as section 2 says, a pad-only player gets silence. This would be seen at once in review.
- **Text**: the page CSS has nothing below 12 px (`src/styles/main.css`). The in-world gauges, labels and readouts are the risk at 800p; the zoom on the triggers may be enough, but Valve's 9 px rule is about interface text, and I would check the help line and any overlays at 1280×800.
- **Resolution**: the canvas follows the window, so 1280×800 should just work. In Game Mode the window is made full screen by Steam's compositor.
- **Performance**: unknown until measured. **(judgement)** Rooms with dozens of lit, shadowed instruments, `antialias: true` and a post-processing pass are within reach of the Deck at 800p and pixel ratio 1, but the pool room's composer and soft shadows are the first places to look. A simple quality setting (shadows off or cheaper, antialias off, a render scale) would protect the 30 fps rule. A quick, free test before any packaging work: open the GitHub Pages build in Chrome in the Deck's Desktop Mode.
- **Native Linux or Proton**: ship a native Linux Electron build, launched with `--no-sandbox` from the Steamworks launch options, and keep the Windows build as the fall-back that Valve would test under Proton if Linux failed.
- **Suspend**: the Deck suspends often. The world store already catches up wall-clock time on resume (up to an hour, `CATCH_UP_LIMIT` in `src/game/save.ts`), which suits a simulation; whether Electron fires `visibilitychange` before suspend is unverified, so the ten-second save interval is the real safety net.

## 6. Other platforms

- **itch.io, HTML5**: upload the existing build as a ZIP with `index.html`; limits are 1,000 files, 500 MB extracted, 200 MB per file, 240-character paths, case-sensitive names, relative paths only ([itch.io HTML5 docs](https://itch.io/docs/creators/html5), read 2026-10-22). The current `dist/` (about 130 files, 15 MB) fits. Options include click-to-launch full screen and a "Mobile Friendly" flag. **(judgement)** This is the cheapest next step of all: no wrapper, no fee, and it can sell or take donations. The absolute `/posters/` path must be fixed first. itch.io can also host the Electron builds as downloads for its desktop app.
- **macOS**: Steam's docs say Mac builds must be 64-bit and notarised by Apple (since 2019-10-14), with the `disable-library-validation` and `allow-dyld-environment-variables` entitlements, and are not compatible with the App Sandbox entitlement ([Steamworks, platforms](https://partner.steamgames.com/doc/store/application/platforms)); a GodotSteam guide updated August 2026 says signing and notarising are not strictly needed on Steam ([GodotSteam](https://godotsteam.com/tutorials/mac_export/)), so check before release. Notarising needs the Apple Developer Program (US$99 a year), a Developer ID certificate and Hardened Runtime; electron-builder and `@electron/notarize` automate it with `notarytool` ([electron-builder, notarisation](https://www.electron.build/docs/notarization)). Mac players are about 2 % of Steam's survey ([Summer Engine guide](https://www.summerengine.com/make-great-games/threejs-game-on-steam), quoting August 2026). **(judgement)** Leave the Mac for later.
- **Mobile (Capacitor)**: `@capacitor/core` 8.5.3 (2026-10-07) wraps a web build in the platform web view (WKWebView, Android System WebView). The game already has touch sticks and pinch zoom. **(judgement)** Possible, but a large first-person WebGL scene on phones, the app-store fees and reviews, and the touch-first interface make it a project of its own rather than a packaging task.
- **Consoles**: none of Nintendo, Sony or Microsoft run a web build as a console game. Nintendo has said HTML5/JavaScript is not supported on Switch (quoted on [html5gamedevs](https://html5gamedevs.com/topic/28282-nintendo-switch), undated); console releases of web games have gone through porting houses or by transpiling (CrossCode's Switch port went through Haxe to C++; [html5gamedevs](https://www.html5gamedevs.com/topic/42198-cross-code-coming-to-switch-discussion/)). Construct claims an Xbox path for HTML5 ([Construct forum](https://www.construct.net/forum/construct-2/general-discussion-17/xbox-ps-66806)), from the old UWP era. **(judgement)** Not realistic for this project; the Deck is its console.

## 7. Costs and paperwork

From [Steam Direct](https://partner.steamgames.com/steamdirect) and [the app fee page](https://partner.steamgames.com/doc/gettingstarted/appfee) (read 2026-10-22):

- Sign the Steamworks agreement, pay US$100 per game (not refundable; recouped once the game makes US$1,000 adjusted gross revenue), then complete bank, tax and identity checks: 15–30 days.
- Bank: account and routing details, account holder name matching the legal identity; a company needs a business account.
- Tax: an online questionnaire sets the US withholding rate; residents of treaty countries give W-8BEN-style information. **(judgement)** As a UK individual that means a W-8BEN, which under the UK–US treaty normally removes US withholding on royalties; check what the questionnaire offers.
- For a first title: 30 days between paying the fee and releasing; a public "coming soon" page for at least two weeks; a review of the store page and of the build, 1–5 days each time (one third-party guide plans for up to seven business days).
- Other costs: none for Steam itself; Apple US$99 a year if a Mac build is notarised.
- Steam requires a disclosure of AI-generated content that ships with the game, shown on the store page; pre-generated content must be declared free of infringing material ([VGC](https://www.videogameschronicle.com/news/valve-has-significantly-rewritten-steams-rules-for-how-developers-much-disclose-ai-use), [TechRadar](https://www.techradar.com/gaming/steam-softens-its-stance-on-ai-generated-content-opening-the-floodgates-to-the-vast-majority-of-games-that-use-it); press reports of Valve's page).

## 8. Licensing and content matters that affect a sale

- **GPL and the Steamworks SDK.** The game is GPL-3.0-or-later (`LICENSE`, `package.json`). The Steamworks SDK is proprietary. Community opinion is that linking it into a GPL program is a licence conflict for anyone but the copyright holder; the usual workaround is a separate proprietary helper process ([steamshim](https://hg.icculus.org/icculus/steamshim/file/f3c91a09913c); [Lemmy discussion](https://lemmy.kde.social/post/2924963)). These are forum views, not legal advice. **(judgement)** As the copyright holder the owner can add a GPL "additional permission" (section 7 of GPL-3) allowing the Steamworks library to be combined, which settles it for the owner's own code; the vendored MIT code (three.js, ThreeJS Water, ThreeVolumetricFire) raises no conflict. Shipping without the SDK avoids the question entirely. Selling GPL software is allowed, but buyers are entitled to the source, which is already public.
- **Assets.** `CREDITS.md` says `fluorescent-ballast-start.wav` is "Not cleared for distribution" and must be replaced or permission obtained before the game is distributed; that applies to a Steam or itch.io release. _(Resolved 2026-10-22: the recording was unused, the fluorescent tubes' sounds being synthesised, and it has been deleted.)_ The CC BY recordings and voice need their credits shown wherever the game is distributed, so a desktop build needs an in-game credits page (or the file shipped and linked).
- **Generated images.** `public/posters/README.md` says the thirty corridor posters are generated images, so the Steam AI disclosure applies.

## 9. Recommended path, and the smallest set of changes

All of this is **(judgement)**.

### Order of work

1. **Measure first, free**: play the GitHub Pages build in Chrome in a Deck's Desktop Mode at 1280×800, with the Deck's controls, and note frame rate per room.
2. **Fix what is wrong in the browser too**: the absolute poster path; audio starting on the first gamepad button; a pad button for a pause menu. These help the web version as much as a packaged one.
3. **itch.io HTML5 page**: a cheap public release and a place to gather players before Steam.
4. **Electron wrapper** in a separate folder (for example `desktop/`), with Electron Forge or electron-builder, producing Windows x64 and Linux x64 builds from the same `dist/`. No Steamworks SDK.
5. **Steamworks**: sign up early (the 15–30 days of paperwork and the 30-day wait run in parallel with steps 1–4), set Auto-Cloud on the save file, set the Linux launch option `--no-sandbox`, put up the coming-soon page.
6. **Later**: achievements through steamworks-ffi-node or steamworks.js from the main process, after the GPL exception; a Mac build if there is demand.
