# Codex critique of the mission 116 plan

The plan has a useful aim: show what the next Use input will do. Its main weakness is the claim that the proposed cue order mirrors the click order. Several room actions sit outside that order, so the acceptance claim that a cue “can never promise what the click will not do” is too strong ([plan](./pick-up-cues.md:116)).

1. **Highest priority — resolve the room’s action before choosing a cue.** `first-person.ts` calls `useWhileHolding` before object handling, ladder use and the room’s ordinary use ([first-person.ts](../../../src/toolkit/controls/input/first-person.ts:396)). Dev0, dev4 and dev5 supply callbacks that can act immediately ([controls-room.ts](../../../src/toolkit/gallery/rooms/controls-room.ts:538), [repair-room.ts](../../../src/toolkit/gallery/rooms/repair-room.ts:657), [bin-room.ts](../../../src/toolkit/gallery/rooms/bin-room.ts:320)). The plan acknowledges that these callbacks cannot be queried, then assumes a marked object’s cue will predict them. That is unproven for unmarked controls and for actions selected by the rooms’ own raycasts. Add a side effect free room action query, or show only a generic ring wherever the room retains first refusal. The plan’s priority diagram and precedence tests should put that query first.

2. **High — `targetFeedback` is feedback, not release precedence.** When carrying, `handling.use` consults custom `targetFeedback` solely to decide whether a `useWhileCarrying` object can pass the click to room use; `release` then calls `heldAction` _before_ `placementAt` and `divert` ([object-handling.ts](../../../src/toolkit/controls/input/object-handling.ts:403), [object-handling.ts](../../../src/toolkit/controls/input/object-handling.ts:234)). In the engineer’s office, `heldAction` returns a software box home even when the aim is over a placement target, and can refuse that return if its support is away ([shell-room.ts](../../../src/toolkit/gallery/rooms/shell-room.ts:721), [engineers-desk.ts](../../../src/toolkit/components/site-dressing/views/engineers-desk.ts:407)). The plan’s diagram puts `heldCue` after `useWhileCarrying`, and its tests put `targetFeedback` ahead of both ([plan](./pick-up-cues.md:330)). Specify one resolved action, using the same priority for querying and execution; otherwise the red × and “fit” glyph can disagree with a click.

3. **High — a “query only” pickup API needs a new contract for room hooks.** The proposed `pickUpAnswer` calls `allowPickup`, but dev4’s `allowPickup` fires a spark and notice when a live part is pulled ([repair-room.ts](../../../src/toolkit/gallery/rooms/repair-room.ts:617)). Polling it at 10 Hz would trigger that effect before pickup. Split the permission decision from the pickup effect, and test that repeated queries leave room state, audio and visuals untouched. Likewise, do not assume every `accepts` or room feedback callback is pure without auditing it.

4. **High — distinguish a blocked aimed bin from a nearby magnetic toss.** `placementAt` returns an aimed target even when it rejects the held object; `release` then stops, without trying `divert` ([object-handling.ts](../../../src/toolkit/controls/input/object-handling.ts:245)). Bin targets have an explicit `accepts` rule, while `nearbyTargetFeedback` reports whether a magnetic toss is available by proximity ([bin-tossing.ts](../../../src/toolkit/components/site-dressing/parts/bin-tossing.ts:166), [bin-tossing.ts](../../../src/toolkit/components/site-dressing/parts/bin-tossing.ts:191)). The plan should test an aimed full or wrong-kind bin separately from a nearby bin. A “put in” cue based only on proximity can promise a toss that the aimed target prevents.

5. **Medium — red pickup cues need a fall-through rule.** When pickup is denied, `handling.use` returns `false` and the room’s `use` runs ([object-handling.ts](../../../src/toolkit/controls/input/object-handling.ts:415), [first-person.ts](../../../src/toolkit/controls/input/first-person.ts:424)). The plan lets a _marked_ use override a red pickup, but an unmarked room use can also act. A red glyph meaning “the click does nothing” is unsafe there. State whether red means only “cannot lift”, or suppress it until the room can answer what the full click does.

6. **Medium — the probe and rendering budget need firmer boundaries.** The current ring raycasts each frame; moving that work to the 100 ms probe is sensible ([first-person.ts](../../../src/toolkit/controls/input/first-person.ts:1725)). Yet one shared raycast is only possible when the room’s handling root and mission 115’s scene probe see the same first hit; the office uses `machines.group`, while rooms also perform their own aim tests ([shell-room.ts](../../../src/toolkit/gallery/rooms/shell-room.ts:718)). Cached hits also become stale when a drawer, door, held object or target moves without camera movement. Recheck visibility and hit geometry when those objects move, and measure the actual raycast count. Keep the controls layer dependent only on callbacks and types it owns, as its layering rule requires ([controls guide](../../../src/toolkit/controls/CLAUDE.md:21)).

7. **Medium — simplify the first visual pass.** Five new gestures, red variants, a red ×, ring size changes and gamepad labels make a crowded reticle. The proposed 34 × 46 SVG puts thin half-pixel edges and small distinctions around a ring whose current size is only 10 or 18 pixels ([plan](./pick-up-cues.md:135), [first-person.ts](../../../src/toolkit/controls/input/first-person.ts:1730)). The lift arrow may resemble mission 115’s slide-up arrow; the down arrow may resemble slide-down; the diagonal “fit” ticks may read like push or focus. First deliver lift, fit/refuse, and a single down/container cue, using the existing ring, then compare screenshots at actual HUD scale. This gives most of the value while the action-query contract is proved.

8. **Lower — close the input and help-line gaps before acceptance.** The touch Use button acts at the centre, but a tap elsewhere acts at the finger’s point; the plan accepts a centre cue that may describe a different action ([first-person.ts](../../../src/toolkit/controls/input/first-person.ts:655), [plan](./pick-up-cues.md:249)). Test both paths and hide or qualify the cue during off-centre touch use. The held-item help line must join the existing per-frame text selection rather than be set only when the object changes, or the next frame will clear it ([first-person.ts](../../../src/toolkit/controls/input/first-person.ts:1466)). The hint must also vary by input: the existing controls specify X, INSPECT and Y ([controls.ts](../../../src/toolkit/controls/logic/controls.ts:58)).

**Questions for the owner:** Ask first about the action language at normal display size, with an in-game mock-up, rather than asking them to choose an abstract arrow description. Keep the software-box versus cupboard-drop question separate: it changes gameplay, so cue work need not decide it. The proposed help-line question is reasonable once the input-specific wording and its place among existing help messages are shown. Ask them one question at a time, as the project rules require.
